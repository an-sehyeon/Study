# 애플리케이션 테스트 관리

## 1. 시험 우선순위

### 최우선

- 화이트박스 테스트 커버리지
- 블랙박스 테스트 기법
- 통합 테스트의 스텁과 드라이버
- 테스트 오라클
- 테스트 케이스 구성요소

### 중요

- 테스트 단계
- 정적 테스트와 동적 테스트
- 확인 테스트와 회귀 테스트
- 성능 테스트 종류
- 테스트 기본 원칙

---

## 2. 테스트 관련 기본 용어

| 용어 | 의미 |
|---|---|
| 오류(Error) | 사람이 요구사항이나 코드를 잘못 판단하거나 작성한 것 |
| 결함(Defect/Fault) | 프로그램이나 문서 내부에 존재하는 잘못 |
| 실패(Failure) | 실행 결과가 예상 결과와 다르게 나타나는 현상 |
| 테스트 케이스 | 입력값, 조건, 실행 절차, 예상 결과를 정리한 문서 |
| 테스트 시나리오 | 여러 테스트 케이스를 업무 흐름에 따라 묶은 것 |
| 테스트 슈트 | 함께 실행하도록 묶은 테스트 케이스 집합 |
| 테스트 오라클 | 실제 결과가 올바른지 판단하는 기준 |

### 관계

```text
사람의 오류
→ 코드에 결함 발생
→ 실행 중 실패 발생
```

## 3. 테스트 기본 원칙

### 3.1 결함 집중

전체 결함의 대부분이 일부 모듈에 집중되는 현상이다.

### 3.2 살충제 패러독스

동일한 테스트 케이스만 반복하면 새로운 결함을 발견하기 어려워진다.

```text
해결 방법: 테스트 케이스를 주기적으로 수정하거나 추가한다.
```

### 3.3 완벽한 테스트 불가능

가능한 모든 입력값과 실행 경로를 전부 검사하는 것은 현실적으로 불가능하다.

### 3.4 조기 테스트

개발 초기에 결함을 발견할수록 수정 비용이 줄어든다.

### 3.5 오류 부재의 궤변

결함이 거의 없더라도 사용자의 요구사항을 만족하지 못하면 좋은 프로그램이 아니다.

### 3.6 테스트의 상황 의존성

금융, 게임, 의료 등 시스템의 특성에 따라 테스트 방법이 달라진다.

## 4. 정적 테스트와 동적 테스트

| 구분 | 프로그램 실행 | 대표 방법 |
|---|---:|---|
| 정적 테스트 | 실행하지 않음 | 리뷰, 워크스루, 인스펙션, 정적 분석 |
| 동적 테스트 | 실행함 | 화이트박스 테스트, 블랙박스 테스트 |

### 리뷰 종류

| 종류 | 특징 |
|---|---|
| 동료 검토 | 동료가 문서나 코드를 검토 |
| 워크스루 | 작성자가 자료를 설명하면서 검토 |
| 인스펙션 | 정해진 절차와 체크리스트를 사용하는 공식 검토 |

## 5. 테스트 단계

```text
단위 테스트
→ 통합 테스트
→ 시스템 테스트
→ 인수 테스트
```

### 5.1 단위 테스트

함수, 메서드, 클래스, 모듈 등 가장 작은 단위를 검사한다.

### 5.2 통합 테스트

모듈 사이의 인터페이스와 데이터 전달을 검사한다.

| 방식 | 진행 방향 | 필요한 더미 모듈 |
|---|---|---|
| 하향식 | 상위 → 하위 | 스텁(Stub) |
| 상향식 | 하위 → 상위 | 드라이버(Driver) |
| 빅뱅 | 모든 모듈을 한 번에 통합 | 일반적으로 없음 |
| 샌드위치 | 상향식과 하향식을 병행 | 스텁과 드라이버 모두 사용 가능 |

### 스텁과 드라이버

- **스텁(Stub)**: 아직 구현되지 않은 하위 모듈을 대신한다.
- **드라이버(Driver)**: 아직 구현되지 않은 상위 모듈을 대신하여 하위 모듈을 호출한다.

```text
하향식 → 하위 모듈이 필요하므로 스텁
상향식 → 상위 모듈이 필요하므로 드라이버
```

### 5.3 시스템 테스트

완성된 전체 시스템이 기능 및 비기능 요구사항을 만족하는지 검사한다.

### 5.4 인수 테스트

사용자나 고객이 시스템을 최종 확인한다.

| 종류 | 의미 |
|---|---|
| 알파 테스트 | 개발자 환경에서 사용자와 함께 수행 |
| 베타 테스트 | 실제 사용자 환경에서 수행 |
| 사용자 인수 테스트 | 실제 업무 요구사항 충족 여부 확인 |
| 운영 인수 테스트 | 백업, 복구, 운영, 보안 절차 확인 |

## 6. 블랙박스 테스트

프로그램 내부 코드는 보지 않고 입력값과 출력 결과를 검사한다.

### 6.1 동등 분할

입력 영역을 동일하게 처리될 것으로 예상되는 그룹으로 나누고 각 그룹의 대표값을 검사한다.

```text
정상 입력: 1~100
비정상 입력: 0 이하
비정상 입력: 101 이상
```

### 6.2 경계값 분석

오류가 자주 발생하는 경계 주변의 값을 검사한다.

입력 범위가 `1~100`이라면 다음과 같이 검사한다.

```text
0, 1, 2, 99, 100, 101
```

```text
최솟값-1, 최솟값, 최솟값+1
최댓값-1, 최댓값, 최댓값+1
```

### 6.3 결정 테이블

여러 조건과 결과의 조합을 표로 만들어 검사한다.

```text
조건이 여러 개이고
조건 조합마다 결과가 달라질 때 사용한다.
```

### 6.4 상태 전이 테스트

이벤트에 따라 시스템의 상태가 변경되는 과정을 검사한다.

```text
로그아웃 → 로그인
비밀번호 오류 5회 → 계정 잠금
```

### 6.5 기타 블랙박스 테스트 기법

| 기법 | 의미 |
|---|---|
| 원인-결과 그래프 | 입력 조건과 출력 결과의 관계를 그래프로 표현 |
| 오류 추정 | 경험을 바탕으로 결함 가능성이 높은 부분 검사 |
| 유스케이스 테스트 | 사용자 업무 시나리오를 기준으로 검사 |
| 비교 테스트 | 같은 입력을 여러 시스템에 적용해 결과 비교 |

### 빠른 구분

```text
입력 범위를 그룹화 → 동등 분할
최솟값·최댓값 주변 → 경계값 분석
조건과 결과 조합표 → 결정 테이블
상태가 다른 상태로 이동 → 상태 전이
테스터의 경험과 직감 → 오류 추정
```

## 7. 화이트박스 테스트 커버리지

프로그램의 내부 코드, 조건문, 분기, 실행 경로를 검사한다.

### 7.1 문장 커버리지

모든 실행문을 최소 한 번 실행한다.

```text
목표: 코드의 모든 문장을 한 번 이상 실행
```

### 7.2 결정·분기 커버리지

전체 조건식의 결과가 참과 거짓을 각각 한 번 이상 갖도록 한다.

```c
if (A && B)
```

필요한 결과:

```text
전체 조건식 결과: True 한 번
전체 조건식 결과: False 한 번
```

개별 조건 `A`, `B`가 각각 참과 거짓을 모두 갖는지는 보장하지 않는다.

### 7.3 조건 커버리지

각 개별 조건이 참과 거짓을 각각 한 번 이상 갖도록 한다.

```text
A → True, False
B → True, False
```

전체 조건식의 결과가 참과 거짓을 모두 갖는지는 보장하지 않는다.

### 7.4 조건·결정 커버리지

다음 두 가지를 모두 만족한다.

```text
각 개별 조건 → True와 False
전체 결정 결과 → True와 False
```

### 7.5 변경 조건·결정 커버리지(MC/DC)

각 개별 조건이 다른 조건과 독립적으로 전체 결정 결과에 영향을 미치는지 확인한다.

```text
조건 A만 변경했을 때 전체 결과가 변경
조건 B만 변경했을 때 전체 결과가 변경
```

### 7.6 다중 조건 커버리지

개별 조건의 모든 조합을 검사한다.

조건이 2개라면:

```text
TT, TF, FT, FF
```

조건이 `n개`라면:

```text
테스트 조합 수 = 2ⁿ
```

### 커버리지 비교

| 커버리지 | 검사 대상 |
|---|---|
| 문장 커버리지 | 모든 실행문 |
| 결정·분기 커버리지 | 전체 조건식의 참·거짓 |
| 조건 커버리지 | 개별 조건의 참·거짓 |
| 조건·결정 커버리지 | 개별 조건과 전체 결과 모두 |
| MC/DC | 각 조건이 독립적으로 전체 결과에 미치는 영향 |
| 다중 조건 커버리지 | 모든 조건 조합 |

## 8. 테스트 오라클

| 종류 | 의미 |
|---|---|
| 참 오라클 | 모든 입력에 대해 정확한 예상 결과 제공 |
| 샘플링 오라클 | 일부 입력에 대해서만 예상 결과 제공 |
| 휴리스틱 오라클 | 특정 입력만 정확하고 나머지는 근삿값 사용 |
| 일관성 검사 오라클 | 이전 실행 결과와 현재 실행 결과 비교 |

```text
모든 입력 → 참 오라클
일부 입력 → 샘플링 오라클
일부 정확, 나머지 근사 → 휴리스틱 오라클
이전 결과와 비교 → 일관성 검사 오라클
```

## 10. 확인 테스트와 회귀 테스트

| 구분 | 목적 |
|---|---|
| 확인 테스트(Retest) | 수정한 결함이 제대로 해결됐는지 확인 |
| 회귀 테스트(Regression Test) | 수정 때문에 기존 기능에 새로운 문제가 생기지 않았는지 확인 |

예시:

```text
로그인 오류 수정
→ 로그인 오류가 고쳐졌는지 검사: 확인 테스트
→ 회원가입, 로그아웃 등 기존 기능도 검사: 회귀 테스트
```

## 11. 성능 테스트

| 종류 | 의미 |
|---|---|
| 부하 테스트(Load Test) | 예상되는 정상 최대 부하에서 성능 확인 |
| 스트레스 테스트(Stress Test) | 한계 이상의 부하를 가해 임계점 확인 |
| 스파이크 테스트(Spike Test) | 부하가 갑자기 증가·감소할 때 확인 |
| 내구성 테스트(Endurance Test) | 장시간 부하를 유지해 메모리 누수 등 확인 |
| 볼륨 테스트(Volume Test) | 대용량 데이터를 처리할 때 확인 |

### 주요 성능 지표

- 응답 시간
- 처리량(Throughput)
- CPU 사용률
- 메모리 사용량
- 동시 사용자 수
